# Render the coast in 3D

## Shared implementation and private trials

Choose the requested mode using the
[shared coastal pipeline contract](../skippercast-discover-coastal-sources/references/coastal-pipeline.md#operating-modes-and-bounded-trial-lessons).
An explicitly assigned private data-only terrain preview uses the reviewed
terrain-only contract, actual depth/mask/uncertainty artifacts and independent
terrain science/visual review. It needs no imagery, habitat interpretation or
publication claim. Paired terrain/imagery render v2.1 retains its imagery rights,
independent correspondence and review gates. A private mesh/PNG proves no website
acceptance. Before product integration, verify that the actual loader preserves
support holes and then collect browser interaction evidence for the requested
view. Private trials do not authorize frontend changes or deployment.

For a website assignment, deliver a visible improvement using its reviewed
terrain and, when paired imagery is requested, reviewed imagery. For a private
terrain assignment, deliver and review the selected data-only preview. Keep the task to rendering and presentation. Offline maps, product consolidation, forecast work, habitat expansion and unrelated source discovery are outside this workflow unless the user changes its scope.

## Select one useful slice

Resume the repository instructions and existing ledger. First read the [upstream mapping handoff](references/mapping-handoff.md). Use only completed reviewed outputs from the designated mapping session. The
private terrain mode requires its terrain-only acceptance; the website mode
requires acceptance for the requested website display and imagery pairing. A validated PARTIAL handoff can supply complete accepted slices; render only its selected IDs and preserve all other holds. Verify artifact identities, geographic support and permission for the selected private or website use before selecting a rendering batch. Do not substitute another region’s data or repeat qualification/ingestion. If no suitable handoff is ready, record the missing prerequisite and stop before starting the timed visual run. Do not invent measurements to complete a region.

Choose one visible defect or improvement. Put its region, visual reference, acceptance checks and relevant source identities in the run brief. Current regions, revisions and jobs belong in the ledger, not this skill.

Preserve original attribution, rights, hashes, coordinate systems, depth datum, coverage masks and native values. Exaggeration or interpolation must remain distinguishable from measured geometry. When imagery is requested, align it with terrain using independent
correspondence evidence. Every mode retains source inspection and coverage
boundaries; a visible surface does not establish support between disjoint cores.

Use the companion mapping skill's
[bounded artifact controls](../skippercast-map-coast/references/bounded-artifacts.md)
with output class `render_preview`. Use a checkpoint for the separately authorized
rendering mission and link its upstream mapping checkpoint/manifest. Do not
change an active mapping mission's immutable output class or reset its budget.
When resuming the same rendering mission, reuse its checkpoint. Pin the
manifest/loader revision and fixed camera. Reuse unchanged accepted assets and
previews; do not repeat native research. Source, rights or policy changes require
only the affected review plus normal exact-head release checks.

## Use cheap, bounded implementation

For an uncalibrated routine task, start with one available `gpt-6-luna` worker at low effort; if unavailable, use an available small model after a task-specific fixture check. Do not assume provider subscriptions or buy access. For comparable tasks, reuse the cheapest setting supported by accepted actual evidence; retain the last successful setting as fallback. Give it a brief of at most 250 words and five relevant paths, exact ownership and acceptance checks. Fork no conversation history; let it read additional targeted dependencies when necessary. The coordinator owns integration, browser verification and releases. Use scripts for extraction, builds, tests and waiting, rather than agents for these tasks.

When a failure produces no new evidence, change approach or narrow the task. Escalate a model-caused implementation failure to `gpt-6.1-sol` medium with the saved reproduction and failed attempt. Missing data, permissions or services need a different action, not a stronger model. Reuse accepted evidence and avoid duplicate discovery.

## Stop development after 60 minutes

Start a timed visual run only when the owner assigns it. Default to a 60-minute wall allowance, including five minutes to checkpoint; a longer run requires a separate owner choice. Use the companion `run_bounded.py` command runner and record UTC start and deadline plus its monotonic subprocess timer. Before each assignment or edit, check remaining time; bound waits and tools to it. Keep workers interruptible and interrupt them at the deadline. A written deadline alone does not enforce a stop. Stop edits and save unfinished diffs, check results and live job handles. Do not restart running CI. Audit time is separate.

Within 15 minutes, seek an actual preview showing the proposed visual change. If it is absent, diagnose the specific blocker and change method or reduce the slice. Tests, documentation and releases alone are not rendering progress.

For a private preview, compare fixed-camera outputs and inspect all selected
cores, explicit holes and the shared depth range; keep browser interaction QA
unknown when only static images were inspected. For an actual website
assignment, compare fixed before/after cameras on the site, including harbor,
shoreline, reef and regional scale across desktop and phone. Reuse unaffected views; inspect changed views for terrain continuity, spikes, void cliffs, imagery seams, depth shading, readable labels and camera/control behavior. Record load/frame timing when a change could affect performance. Review rendered output early, not only at the end.

## Review, deploy and improve

After stopping, use an independent `gpt-6-astra` medium reviewer with the bounded diff, screenshots, source receipts, check results and action log. It assesses visual quality, data honesty, correctness and avoidable rework, then recommends a small skill correction supported by evidence. Resolve blocking findings before release; if more implementation is needed, carry it into the next authorized run. Follow repository merge/deployment gates. After the deadline, save results and existing job handles. Release requires the task's explicit publication scope; this skill does not authorize it.

Keep one receipt: objective/region; start/deadline/stop; changed paths; visible result and data-supported area; before/after views; attempted/passed checks; review findings; live jobs; blockers/next action; available model, token, time and rework evidence. Do not invent unavailable usage or claim a cheapest proven setting from a simulation. Read [calibration](references/calibration.md) only for the end-of-run audit and model evidence.

Save the retrospective and propose the smallest evidence-backed skill correction
for a separate reviewed revision. Do not edit the running skill, start timed
trials, or extend into another region without a new assignment. Include
planned/attempted/usable work, artifact paths and coverage method, raw
input/cached/output usage (unknown where unavailable), elapsed time, retry counts,
remaining bounds, blockers and next action. Report useful-output yield by class;
never infer dollar cost, waste or savings from token totals alone.
