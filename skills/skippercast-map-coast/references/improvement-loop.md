# Improve through bounded mapping rounds

Use only when the owner requests a timed experiment or repeated improvement
loop. Record the exact requested round count and duration. A request for four
60-minute rounds authorizes those four renewals, not an indefinite loop or a
longer run afterward. Keep one compact loop checkpoint that references the
previous evidence rather than copying its history or creating a new source
catalog. The [progress control](progress-control.md) still applies within each
round; a 60-minute observation window does not waive its token, active-time,
source-attempt or no-progress limits.

## Before Round 1

Use the prior audit to select one concrete workflow optimization. Prefer a cheap
change tied to a demonstrated failure. Test it and install the reviewed skill
before starting the clock. Record its exact version. Limit initial setup and
each subsequent audit/skill revision to 150,000 measured uncached-input-plus-
output tokens and 20 active minutes when those measurements are available;
record unavailable measurements and preserve a blocked handoff instead of
turning the audit into another large research project. Required scientific and
protected CI checks cannot be waived; deterministic waiting is recorded apart.

Select one candidate with a real downstream publication path. If none is
executable, test a bounded preflight or one named preparation change and say
that the round has no currently runnable publication. Do not fill the hour
with unrelated source qualification. Known negative routes survive every round.
Another round number is not new evidence for retrying them.

Record a fresh public baseline and retain its provenance; external agents'
concurrent additions are not this experiment's output. Fix the claimed outcome,
source/reach/window, scientific method and input hashes. Record all early stop
conditions before execution. Use actual shared usage, not a closed old goal's
frozen counter. Keep cached input and generated output accounting separate.

## Run one 60-minute observation window

Record actual start and deadline in UTC; set `progress_control.deadline_utc`.
The deadline applies even to finalization. Call the guard before every stage
and new dispatch. Do not start a batch unlikely to finish with its review and
publication evidence before the deadline. Stop active model work earlier when
the effort or stagnation guard fires; record the reason and leave a real
deterministic observer or exact resume command. Do not keep a model busy until
the timer expires. A blocked round is a useful negative result, not map growth.

Use one deadline wakeup in the current chat, when supported. A repeating wakeup
may be updated after each audit to the next round's actual deadline; audit time
must not shorten the next round. Persist the automation ID and verify its next
run time. Never create a competing schedule or leave it enabled after the
authorized final audit. Follow the host's scheduling and permission rules.
Local execution depends on the app and computer being available; a missed
wakeup remains missed and cannot be backdated as executed work.

At the deadline, stop dispatch and freeze the round. Safely checkpoint local
work and preserve external job IDs; do not cancel an unsafe in-flight publisher
or launch recovery without reconciling its state. Report pending publication
as pending. A result verified later is recorded as late completion from its
originating round and counted once, not credited to two rounds. The audit's
cutoff statistics do not silently change afterward.

## Audit, change, then start the next round

Use only the round's compact receipts and the changed implementation. Report:

| Result | Evidence |
| --- | --- |
| Actually published additions and expansions | Own release identity plus complete regional public readback; distinguish interpreted and ranked output. |
| Native measurement / physical habitat delta | Deduplicated native unions in the same scope; unknown stays unknown. |
| Reusable private results | Artifact hashes, exact saved stage and remaining downstream gates. |
| Effort | Shared measured token metric/scope, active time, deterministic wall wait and audit/update overhead separately. |
| Failures | Reproduced error, source no-delta, rights/geometry/policy hold, cache/runtime problem or deadline/allowance stop. |
| Learning | What worked, what broke and one specific next change with its acceptance test. |

Compare public throughput and useful private handoffs against the previous
round using the same accounting scope. Do not rank a round as successful merely
because it ran longer, generated more artifacts or merged more code. Distinguish
invalid-source rejection working correctly from a pipeline failure.

Make only the skill change supported by the observed failure. Prefer changing
selection, caching, dispatch or observation before inventing more framework.
Add a regression control for a fragile changed rule; retain mandatory review
and exact-head CI. Reuse unchanged original-source evidence. If no new learning
warrants a rule change, record that explicitly; do not churn the skill to make
the loop appear productive. A genuinely blocked revision saves a handoff and
stops the loop until the required input is available.

Start the next 60-minute clock only after the audit and reviewed skill revision
are complete, or the documented no-change decision passes. Carry negative
findings and scientific holds forward. The owner's requested next round renews
the calibration allowance; it does not reset failed-source history. Update the
same wakeup to that round's new deadline and confirm it. After the requested
final audit, stop the automation and report the cross-round comparison, remaining
gates and whether a longer run has an executable path. Do not start the longer
run without its own authorization.
