# Run a bounded parallel habitat-expansion pilot

Use this procedure when the owner requests parallel mapping or a timed pilot.
The duration is an observation window, not permission to prolong a blocked
batch. Record the UTC start and deadline and the user's reporting preferences
in the existing coordination issue and private progress checkpoint.

## Choose one release before filling the worker pool

Inspect current main, relevant open PRs, the ledger and the latest retained
receipt. Select a source/reach with a positive physical opportunity. Acceptance
is a new, correctly labelled visitor-visible habitat outline verified in the
published regional archive and map. A probe, merged feature or green refresh
does not meet that acceptance on its own.

If the publication contract is missing, assign one implementation worker to
that specific positive batch and retain an independent reviewer. Pause discovery
once two useful qualified handoffs are waiting. Do not employ more discovery
agents to enlarge a queue that cannot yet publish.

## Assign bounded ownership

Use the concurrency available in the current session; do not assume that a
requested increase overrides its hard limit. A useful starting arrangement is
one coordinator, two bounded source/processing workers and one reviewer.
Reassign an idle source slot to implementation when that is the bottleneck.

- The coordinator alone integrates shared catalogs/skills, opens or reconciles
  release PRs, dispatches public jobs and verifies releases.
- A worker owns an exact reach, source pair and method in an isolated worktree
  or private output directory. It may process up to three bounded reaches.
- The reviewer independently checks original evidence and the exact code head;
  it does not implement the change that it reviews.

Use the existing issue/checkpoint for claims. Before assigning a task, check
other active chats and agents for the same source/reach/method. Never commit to
another worker's branch. Use focused branches and the existing protected PR
flow; two independent branches can run concurrently, shared writes cannot.

Where the owner permits model selection, focused qualification and deterministic
run supervision can use an economical model such as Luna with sufficient
reasoning effort. Use Sol for integration, ambiguous code changes and independent
review. Respect an explicit user choice; do not silently switch the coordinator
or escalate to Astra. Give fresh workers a bounded brief and relevant paths,
not the full conversation. Model names are choices, not measured cost savings.

## Require a handoff that can be executed

Each worker saves, in the established private progress location:

- claim, source lineage/IDs/hashes, baseline commit and receipt hashes;
- exact command, runtime, output paths, resource bound and observed duration;
- additional valid measured union and additional physical habitat union;
- retained patches versus raw fragments; projected and WGS84 geometry validity;
- ranked versus interpreted/unranked output and preliminary screen results;
- rights, quality and spatial holds, with the failing test or source evidence;
- completed stage, next reproducible command and who must execute it.

No private geometry or survey originals belong in a public issue or PR. A
missing current screen is a distinct hold, not proof of MPA intersection.
Polygon totals from different sources/reaches must be deduplicated before they
become a combined area or count. Invalid geometry cannot enter a public batch.

## Switch work instead of repeating failure

Keep physical mapping independent of final publication holds. A held source can
produce private evidence while another qualified batch advances. After two
failed attempts at the same problem, change source, reach or method using the
diagnostic evidence. Within 20 active investigation minutes, require a usable
batch or a demonstrated release-blocker fix. New metadata or debugging output
alone does not extend that window; checkpoint and switch to an independent task.
If none exists, record the exact external dependency rather than run maintenance
as expansion. Deterministic jobs run without model activity; use completion
events or bounded checks, not repeated polling of unchanged jobs.

Preserve failures as well as successes. A code fix counts as pipeline progress
when a test or real receipt reproduces the old blocker and demonstrates its
removal. It remains separate from public habitat expansion.

## Checkpoint and reconcile

For the owner's requested pilot, give brief updates about every three minutes
of active work and a milestone summary every 15 minutes. Summarize new evidence,
the deliverable, remaining blocker and next action. Do not manufacture activity
updates while an unchanged deterministic job runs. Save completed commands and
evidence before a turn ends or a worker changes tasks.

At the deadline, reconcile against the immutable starting baseline:

| Result | Evidence required |
| --- | --- |
| New measured coverage | Difference of valid native measurement unions in the same scope |
| Additional physical habitat | Valid deduplicated polygons outside baseline habitat |
| Legally screened candidates | Current whole-polygon screen and source-rights receipts |
| Actually published additions | Regional manifest/archive readback and visitor map check |
| Pipeline blocker removed | Reproducible before/after failure test or run receipt |
| Resources and throughput | Observed wall time, completed/rejected batches, queue wait and reported usage |

Report ranked terrain, measured rough search areas and producer-interpreted
habitat separately. An interpreted class area earns no new-measurement or
Tier-2 credit. Polygon splitting and reranking are not expansion. Record removed
or revised areas, too. A deadline does not make incomplete coastline complete.

Report actual usage only when a tool or provider supplies it. State its scope
and limitations; aggregate goal tokens are not a billing statement, per-agent
breakdown or cache statistic. Never estimate a cost as measured. Missing timing
or usage stays unavailable.

## Decide whether to increase the pool

Recommend more workers only when the pilot demonstrates independent useful
batches, actual public additions, no ownership/cache conflicts, and processing
capacity that can absorb them. Compare completed releases per observed wall
hour and integration/review waiting time with the starting pool. Four agents
already waiting on one contract, legal screen, publisher or storage bottleneck
will not benefit from more discovery agents; repair that stage first.

Do not promise a linear speedup or double a pool automatically. If concurrency
is capped, explain that limit and propose a separately authorized configuration
or subsequent trial. Preserve the next ready batch and unresolved dependencies
in the same checkpoint so the next session resumes instead of re-auditing.
