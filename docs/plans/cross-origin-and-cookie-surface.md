The passkey check is `0 < expires_at - now < 15 days`: exactly 15 days does **not** renew; an expired row is deleted and does not return an identity. On renewal the DB expiry is updated first and `SessionUser.renewed` carries the serialized cookie. After the handler, `securityHeaders` appends it only if the response has **no** `Set-Cookie`, cloning the response if needed; an explicit logout/account clear is not overwritten. Renewal depends on an identity lookup, not merely on sending the cookie to a public asset or feed (`server/auth.ts:8–9,64–76`; `server/middleware/context.ts:29–33`; `server/middleware/security-headers.ts:8–17`). Successful registration or sign-in revokes the old current session before issuing a new token; ending other sessions removes their server rows without clearing other browsers' cookies. Account deletion removes all that user's session rows; scheduled pruning also removes expired rows (`server/auth.ts:140–157,179–196,239`; `server/routes/account.ts:39–43`; `server/trips.ts:153`; `server/index.ts:26–34`). The last-known cache's `Set-Cookie` test is a response-header check, not a third cookie reader (`server/cost-ceiling.ts:169–180`).

## 2. R2 — Worker CORS, Origin checks and OPTIONS

**Response headers.** These are the source-defined `Access-Control-*` headers. In this table, “unlisted” refers to the request's `Origin` header, not the destination hostname.

| Response path and method | Header and value | What an unlisted origin receives |
| --- | --- | --- |
| `GET /feeds/*` (GET registration; Hono's HEAD fallback normally strips the body). Responses using the constructed feed headers, including normal/range/conditional responses and some error responses; cached feed responses can reuse the headers. | `Access-Control-Allow-Origin: *`; `Access-Control-Expose-Headers: ETag, Content-Range, Content-Length, Accept-Ranges, X-Feed-Generation`. Exposure names do not guarantee a field is present. | Same feed status and headers as any other origin; browser access for noncredentialed CORS requests that do not require preflight. No blanket grant on every feed response: invalid keys, missing release mapping, some seafloor gate failures, the archive-race error and certain unavailable responses return outside the shared headers; rate limiting can answer before the feed code (`server/routes/feeds.ts:10–14`; `server/feeds.ts:312–350,352–415`). |
| Degraded last-known hit, GET only: `/feeds/*` except `/feeds/tiles/seafloor/*`, exact `/api/daily`, `/api/forecast`, `/api/intelligence`, `/api/habitat`, and `/api/om/*`. | Preserves stored headers, appends `X-SC-Degraded, X-SC-Last-Known-At` to `Access-Control-Expose-Headers`. Cross-origin script cannot read it via CORS (`server/cost-ceiling.ts:216–219,241–249`). |
| Other downstream responses marked by the same degraded middleware (including non-GET, errors outside the eligible set, and eligible successful fallbacks). | Appends `X-SC-Degraded` to `Access-Control-Expose-Headers` and sets `X-SC-Degraded: cost-ceiling`; leaves any original allow-origin intact. | Underlying route outcome and allow-origin behavior unchanged, with the additional marker; exposure alone does not authorize a cross-origin read (`server/cost-ceiling.ts:222–225,241–250`). |

No Worker-authored `Access-Control-Allow-Credentials`, `-Allow-Methods`, `-Allow-Headers`, `-Max-Age`, or other `Access-Control-*` field beyond the table (pinned search above). This is not a claim about arbitrary headers returned by the platform asset binding. The map shell's `crossorigin="anonymous"` is an HTML preload setting for same-origin `/regions/.../region.json`: it uses same-origin credentials, matching the plain fetch with `init: {}`. It is not a response CORS grant or an instruction to omit same-origin cookies (`server/routes/assets.ts:115–130`; `web/early-reads.ts:31–45,120–126`).

**Origin checks.** `requireOrigin` compares the raw header by exact membership; missing or unlisted yields `400 {"error":"origin rejected"}` once the request reaches the check. Production list: `https://skippercast.com` and `https://www.skippercast.com`; extra entries are trimmed comma-separated values restricted by `context` to lowercase HTTPS host syntax or HTTP localhost with optional port. Preceding gates can answer first; none of these checks sets allow-origin, even on a match (`server/http.ts:24–27`; `server/config.ts:3–7`; `deployments/production.json:2–6`; `server/middleware/context.ts:26–28`; `server/middleware/error.ts:12–22`).

## 3. R3 — Public privacy-page comparison

> We set one cookie, `__Host-sc_session`, when you sign in. It keeps you signed in for 30 days from your last use and is not used for tracking.

`dist/privacy.html:52–55`; the table also says “Until they expire (30 days after last use) or you sign out” (`:74–76`). The passkey cookie name, sign-in purpose and nominal 30-day window agree with the Worker. Its code uses the token hash for account-session lookup, not as a feed or Advisor identifier; it does not restart the clock on every use (§1). The page does not mention **`sc_adv`**, which is issued independently of account sign-in and identifies Advisor web contacts for chat and upload (§1). These are source observations, not statements about whether the gated feature is on in a live environment.

> Your home port, boat profile, comfort limits, language, map choices, a private map log (up to 500 entries, including positions you pick on the map) and saved offline map data are kept in your browser’s storage and never sent to us. Clearing your browser’s site data removes them.

`dist/privacy.html:136–142`. There is browser-side storage separate from HTTP cookies: local preferences (`web/ports.ts:148–172`; `dist/boat-handling.js:92–106`; `web/limits.ts:44–60`; `web/i18n-core.ts:71–96`; `web/state.ts:151–165,323–332`), a local 500-entry log (`web/private-map-log.ts:6–7,50–60`) and Cache Storage for offline data (`web/trip.ts:178–212`; `dist/sw.js:206–224`). Clearing those local stores does not remove independent server records. In particular, saving a trip alert explicitly sends trip limits and can send a projection of the saved boat, which the Worker stores; this is a separate save flow from ordinary local preference storage (`web/app/TripAlerts.tsx:65–70,340–347`; `web/alerts.ts:72–74`; `server/routes/trips.ts:21–30`). The page itself lists saved-trip settings, including limits and boat, in the account table (`dist/privacy.html:78–81`). The Advisor panel also keeps an open/closed flag in localStorage, separate from its server-read cookie (`web/advisor/chat.tsx:5–25`; §1). No privacy wording or policy decision is made here.
