## R2. Bypasses and what readers do

- **Returning is not throwing.** Any route-local `json(..., errorStatus)` or gate return bypasses the error mapper but uses J. That covers local JSON replies in Admin, Advisor, Auth, Boat, Catch log, Coast data, Feedback, Fleet, Jobs, OM, Public, Spots, Subscriptions and Trips (the R1 sources show each); Account's protected errors come from P/mapper, and Telemetry uses the limiter and throws rather than returning local errors (`server/routes/account.ts:12–44`; `server/routes/telemetry.ts:12–17`). Both `tooManyRequests()` and the cost-ceiling replacement skip the mapper and `json()` but keep string `error`; only those paths add their respective 60s/600s retry header (`server/edge-cache.ts:92–95`; `server/cost-ceiling.ts:216–219`; `server/middleware/error.ts:22`). The common security and ID wrappers still run on ordinary responses (`server/app.ts:46`; `server/middleware/request-id.ts:15–21`; `server/middleware/security-headers.ts:8–18`).
- **A strict string reader:** `web/admin/api.ts:134–140` catches JSON parse failure and uses `HTTP <status>` for plain text, HTML, empty bodies and OM's Boolean `error`. It takes a string `error` even if extra fields are present; it parses bytes rather than requiring JSON MIME, so a mislabelled but valid feed JSON body can still produce its message. This describes what that reader would do on those shapes, not which routes it calls. `dist/account.js:46–47` (loaded by `web/account.ts:96–100`) is less strict: missing/invalid JSON falls back to default copy and a truthy Boolean error would be stringified by `Error`, not read from `reason`. `web/alerts.ts:49–51` uses its own copy on parse failure or missing `error`.
- **Different reader goals:** `web/account.ts:34–49,61–72` does not display `error` for the session probe; non-ok or unparseable responses mean `offline` and no admin flag. `web/shared-fetch.ts:25–48,63–71,118–130` does not inspect `error` at all: it only shares selected static JSON requests, evicts shared non-ok results and propagates body-read rejection; API requests pass through. The forecast helper rejects non-ok with `HTTP <status>` *before* reading JSON; its `reason` check is for a parsed ok response (`dist/forecast.js:223–234`).
- **Raw branch inventory:** Advisor text/HTML/empty media errors, Admin page misses, Assets, Coast data retired/range/method responses, Coast pages and Feeds all have non-helper branches listed in R1. For ordinary JSON consumers, names like `signIn`, `request_id`, `degraded`, `replacement` and Fleet `errors` are additions, not replacements for the string; the incompatible JSON type is OM's Boolean. None of the table's text/HTML/empty branches gives a JSON reader a string `error` (`server/routes/om.ts:29`; raw branch sources in R1).
