# Alarm issue wording

**Recommendation:** Use “Feed source or coverage problem” for the shared feed alarm; say in the first line whether it needs attention now or is advisory.
**Why:** The November 21 alarm did have late critical sources in one region, but an earlier alarm with the same title was opened for a preview-region fetch timeout with no critical source past its limit ([November 21 run](https://github.com/Grahammmm/skippercast/actions/runs/44907608604), [November 18 run](https://github.com/Grahammmm/skippercast/actions/runs/44366529023)).
**Next:** Make the other titles describe what the check actually found; the exact copy and owner approvals are in §3. This report changes no alarms.

Source checked at `origin/main` commit `7335068efd2627dd2a0ba9bea39f09e86a8f252d` (`git rev-parse origin/main`). All file and line references below are at that commit.

## 2. Where the title or first line goes too far (C2)

- **Feed source — severity, confirmed.** [November 18](https://github.com/Grahammmm/skippercast/actions/runs/44366529023): “Daily data feed: 6 degraded source(s), none critical past 48 h.” The other source warning also says “Live regional feed shelter-cove-north-mendocino: 4 degraded source(s), none critical past 12 h.” What triggered the same “Critical feed source degraded” title was: “Public Live regional feed humboldt-bay-cape-mendocino could not be fetched: The read operation timed out (not an active region; reported, does not fail)”. The workflow opens for either `degraded` or `partial`; a preview-region fetch failure alone sets `partial` (`.github/workflows/feed-freshness.yml:79–92`; `scripts/check_feed_freshness.py:364–383`). [November 21](https://github.com/Grahammmm/skippercast/actions/runs/44907608604) is a different case: “Daily data feed: 8 degraded source(s), none critical past 48 h.” is only about the daily feed; the same report says “Live regional feed point-arguello-conception: 2 critical source(s) degraded past 12 h while others of the same kind are not (partial outage; reported, does not fail).” Here *critical source* is accurate; a critical outage is not. Leading with the publish time of an unaffected feed does not tell the reader why either alarm opened (`scripts/check_feed_freshness.py:322–340,386–404`).
- **Fishing rules — certainty, confirmed.** “Rules status missing in a beta region” asserts that a status was seen missing. [The probe-failure issue](https://github.com/Grahammmm/skippercast/issues/2265) says “At least one species in a Stage 1 region reads \"Check rules\", or a region's probe could not run. Per-region results follow.” Its output says `morro-bay (probe exit 1)` and `ERR_MODULE_NOT_FOUND`: the check could not establish the status. The [older title](https://github.com/Grahammmm/skippercast/issues/2196), “Rules card is blank: no species has a season status”, also claims *all* where that same first line says “At least one … or …”. That older title is no longer the create string. The [open rules issue](https://github.com/Grahammmm/skippercast/issues/2515) shows actual unknown results, not just a crashed check.
- **Feed stale — freshness, conditional.** [The dated data-feed issue](https://github.com/Grahammmm/skippercast/issues/2476) says “STALE data: last published 2026-11-15T18:53:25Z (36.3 h ago), 0.3 h past its 36 h limit.” Title and first line agree in that case. But the writer also emits `STALE {feed}: no readable publish time{reason}; cannot say when it last published.` (`scripts/feed_stale_alert.py:43–50`). Neither that line nor the title can establish age if the feed could not be read. For `freshness-check` the reason is exactly `the freshness check crashed or reported stale without naming a feed` (lines 125–139); that isn't a feed name or proof that one was late. A live occurrence of either unknown variant in the week is **UNVERIFIED**; these are code paths, not observed issues (§1).
- **Site — scope and certainty, confirmed historically.** “Site is down” covers the whole site, while one failed path is enough (`scripts/site_uptime_alert.py:112–117,124–139`). [The earlier issue](https://github.com/Grahammmm/skippercast/issues/1349) opens “The site did not answer on:” but lists `- /api/health 403`, `- / 403`, and `- /map 403`: the check received refusals, not silence. Current code can also report `not JSON 200` for the health route and can detect refusals (`scripts/site_uptime_alert.py:87–99,133–138`). The current all-refused caveat itself says “Every path was refused (4xx), not unreachable: check edge bot rules before treating this as an outage.” It tests the *failed* paths only, not those that passed (lines 112–117,133–135). No current-week issue (§1).
- **Coast data — certainty, confirmed.** “Coast data path is down” and “The coast data service did not answer on:” overstate [this single-path result](https://github.com/Grahammmm/skippercast/issues/3096): `- /feeds/tiles/seafloor/manifest-morro-bay.json habitat unavailable 200`. The path answered; its manifest did not pass the readiness check, which checks status, region and expiry (`scripts/site_uptime_alert.py:76–86`). The result does not say which of those tests failed.
- **Fleet — certainty, conditional.** “Fleet AIS listener or processor is stale” treats an unconfirmed result as measured. The unknown-reply body reads `Fleet AIS health for {region} is unknown: the Worker's health route did not return a complete, consistent reply.` (`.github/workflows/fleet-health.yml:43–61,76–90`; `{region}` is the configured region). The workflow can also flag a quiet message stream independently of a late heartbeat or processor: [a November 15 follow-up](https://github.com/Grahammmm/skippercast/issues/2264) says “Fleet AIS health for CA (stale after 3 h): heartbeat 2.53 h old, last_message 4.99 h old (stale), processed 2.52 h old. Likely cause: no-messages.” The two issue-opening bodies in the week did show late checks; a live unknown-reply issue in that window is **UNVERIFIED** (§1).
