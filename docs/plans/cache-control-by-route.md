# Cache-Control by route

| Summary | What the code says |
| --- | --- |
| Ordinary feed rotation or withdrawal | A warm edge can serve the former body for 60 or 300 seconds; it checks the logical URL before looking up the current release. An ETag or `X-Feed-Generation` on that reply does not make it current (`server/feeds.ts:165,207–240,312–322`). |
| Longest HTTP windows | A year on content-named basemap URLs, bundled assets and versioned glyphs; new names solve replacement, not withdrawal of an old URL (`server/feeds.ts:166–170,346–348`; `scripts/client-build.mjs:32–39`). The cost ceiling can replay a seven-day server-side copy but sends it as `no-store` (`server/cost-ceiling.ts:38,169–218`). |
| Missing header | Mainly specific errors, one empty POST acknowledgment and static pass-through **at the Worker**. Normal account, health and non-cacheable JSON replies use `no-store`, not `none` (`server/http.ts:7`; `server/routes/account.ts:13–43`; `server/routes/public.ts:21–24`; details in R1–R3). |

Source: locally staged `origin/main` at `26aa28ab1ce4e883c0850cdb7f1243c4ed48c07e` (commit dated 2026-11-21). This is an offline source audit, not a measurement of deployed Cloudflare rules, `Age` headers or browser cache state.

## R1. What each route family sends

`none` means no header set by that response path, not `no-store`. For pass-through, the binding may supply its own value. `JSON` below means the shared `json()` response: `no-store` by default (`server/http.ts:7`). `PUBLIC_TTL` is exactly `public, max-age=300, s-maxage=300` (`server/config.ts:10`). Routing order matters: cost ceiling and canonical redirect precede the routers; bare `/feeds` and `/api` are asset routes, unlike `/feeds/*` and `/api/*`; the asset catch-all is last (`server/app.ts:44–76`).

## R2. How long former bytes can still be served

These are policy windows from insertion of a fresh copy, or estimates where layers interact. If replacement happens just after insertion, almost the full window remains. They are not disk-retention or purge guarantees. For an ordinary HTTP cache chain preserving response age, do not add the TTL per hop (HTTP model: RFC 9111 §§4.2–4.2.3). The Worker passes cache-hit headers through; it does not calculate a remaining client TTL (`server/edge-cache.ts:31–35,58–74`). **Estimate:** if a hit or cache-generated validation is presented as fresh to a downstream cache without the prior age, a late hit could extend reuse by another client TTL; no end-to-end age bound was measured. The table separates code-managed edge storage from what a browser or other HTTP cache is told.

| Public family | Longest configured reuse and what cuts it short |
| --- | --- |
| Ordinary `/feeds/*` R2, including mutable JSON, tiles and date-only basemap | Edge/browser: 60 s or 300 s by filename. The edge keeps whole objects only up to 32 MiB and uses logical path plus Worker build, **not** release generation. A healthy miss reads the current pointer and refuses absent members; R2 ETag validates that read, but an edge ETag/304 can validate the old copy. `If-Match`/`If-Unmodified-Since` go to R2; a new query or client `no-cache` is not a Worker bypass. **No withdrawal invalidator before TTL** for a normal hit (`server/feeds.ts:108–127,165–170,203–240,312–322,354–397`; `tests/test_feeds_cache_first.mjs:94–137`). |
| Content-named basemap `/feeds/tiles/basemap/...-<hash>.pmtiles` | Browser and eligible edge entries: 31,536,000 s (365 days). New bytes get a new content name; this protects replacement via changed links, **not revocation at the old URL**. R2 ETag/range consistency is not a purge. Larger objects don't enter the normal whole-file edge cache but still carry the browser TTL (`scripts/basemap/regions.py:110–115`; `server/feeds.ts:166–170,203–240,346–348,382–411`). |
| Bundled `/feeds/tiles/*` fallback | Same 60/300 s or immutable year according to the logical key; no normal feed edge write on the asset branch. Optional asset validators support conditional range use, not early invalidation. **No separate withdrawal bound**; an asset still shipped under the key can answer even after R2 removal, so the cache window applies after the asset also stops serving old bytes (`server/feeds.ts:192–200,346,400–411`). |
| Habitat, daily and forecast JSON | Browser and normal edge: 300 s. Build plus route parameters (daily part/region; habitat/region; forecast/region), not release generation. **Nothing bypasses the TTL on same-build replacement** (`server/routes/public.ts:26–34,84–112`; `server/edge-cache.ts:22–28,58–74`). |
| Intelligence JSON | Browser and normal edge: 60 s. Same build/region scheme; forecast misses can fill intelligence and vice versa. **No generation key or validator** for the derived response (`server/routes/public.ts:101–112`). |
| OM forecast, marine and model metadata | Browser and normal edge: 300 s. Build/query key, **no model-cycle key or outgoing validator** (`server/routes/om.ts:17–35`; `server/config.ts:9–10`). |
| Port and boat HTML; species HTML; advisor sitemap | Browser and normal edge: 300 s (port/boat), 900 s (species), 3,600 s (sitemap). The Worker checks gates and keys by build + D1 pages version + relevant flags, with resolved language in the HTML key. A version bump makes old entries unreachable to new Worker reads, not to a browser holding a fresh old URL. **No early edge invalidation for changes that don't bump the key** (e.g. time/feed-only changes); no early browser invalidation (`server/routes/advisor.ts:629–657,668–686`; `server/advisor/pages/data.ts:17–21`; `server/advisor/pages/render.ts:204–214`). |
| Port/species 301s, contact card and QR; canonical 301 and dynamic robots | Browser/any honoring shared HTTP cache: 86,400 s (port/species 301s, card and QR) or 3,600 s (canonical and robots). No explicit Worker cache entries on those response paths. **No version or validator** to notice a changed target, number or sitemap line sooner (`server/routes/advisor.ts:411–444,665–675,691–695`; `server/middleware/canonical.ts:7–25`). |
| Generated immutable assets and versioned glyphs | Advertised browser/shared freshness 31,536,000 s. Bundler hashes and glyph-content versions make replacements addressable by a new URL; **no recall for the old URL** (`scripts/client-build.mjs:3–5,32–39,116–139,148–167,204`). |
| Generated region/data rules | Short rule: 120 s fresh plus up to 300 s stale during revalidation where supported (420 s total, estimate; not a measured CDN TTL). **No invalidator in that rule**. Safety overrides: 0 s unconditional reuse, must revalidate; no long window declared even if the asset has a platform validator (`scripts/client-build.mjs:41–58`; `tests/test_client_build.mjs:182–203`). |
| Last-known cost-ceiling copy | Edge only: up to seven days from the last eligible normal save, not from the feed's generation time. Key is origin/path/query/Range, **no release, build or ETag check on replay**; no refresh on normal marked edge hits. A degraded request may see withdrawn bytes before routing reaches the current release check; the returned `no-store` stops ordinary HTTP recaching, not the server replay. Seafloor is excluded. The daily ceiling resets at UTC day roll, but a still-held copy can be used again upon degradation (`server/cost-ceiling.ts:38,61–64,111–145,169–218,234–251`). |
| External public feed cache and boat lookups | Edge only: 300 s per upstream URL, and 30 days per normalized boat query respectively. **No source revision/validator** at either cache lookup. Downstream routes have separate policy; boat JSON is `no-store` (`server/feeds.ts:427–440`; `server/routes/boat.ts:20–43`). |

Separate browser storage: the service worker can retain public feed/data successes and serve a saved copy after a fetch rejection; it uses an entry-count limit for recent data, not the HTTP max-age as a replay deadline. It admits a separate basemap/pack path and excludes seafloor feed URLs from ordinary data caching. Thus even the R2 HTTP windows above are not deletion bounds for offline copies (`dist/sw.js:41–79,144–171,224–255,378–407`). Coast HTTP is `no-store`; explicit coastal offline snapshots are a separate workflow (`dist/sw.js:258–283`).

## R3. Changing data without a Worker header

| Family | What is actually missing, and expected browser behavior |
| --- | --- |
| Changing public JSON, status and account | None of the normal dynamic successes audited are missing the header: feed/API successes use R1's explicit rules; `/api/health`, `/api/advisor/health`, session, privacy, auth, trips and other private JSON are `no-store`. The `/status` shell is `no-store` when routed through the Worker; the page itself calls `fetch` with `cache: 'no-store'`, which is not a bypass of the Worker Cache API (`server/routes/public.ts:21–24,89–112`; `server/routes/advisor.ts:79–83`; `server/routes/account.ts:13–43`; `server/routes/trips.ts:17–19`; `server/routes/assets.ts:34–42,107–114`; `dist/status-page.js:225–236`; `tests/test_feeds_cache_first.mjs:106–123`). |
| Static pass-through that can change | Stable URLs such as static robots, `precache.json`, unversioned glyphs and ordinary files outside the custom rules get no Worker override. **Estimate:** platform defaults may supply revalidation and validators (the build comments expect this for unversioned glyphs); if the final response really has neither explicit freshness nor an `Expires` value, an eligible GET can be stored and assigned heuristic freshness, sometimes based on Last-Modified. No fixed lifetime can be read from this repo (`server/routes/assets.ts:107–110,141–145`; `scripts/client-build.mjs:34–58,204–205`; HTTP model: RFC 9111 §§3,4.2.2). |
| Bare missing responses and method refusals | **Estimate:** a bare GET 404 can be stored heuristically, so a newly available URL can briefly still look missing; no repo TTL on those paths. 405 is also a heuristically cacheable status on an eligible method, but these guards deny methods other than GET/HEAD, so ordinary browser reuse is unlikely. Twilio status POST 204 has no changing read body and no explicit freshness; not expected to become a reusable cached GET or POST reply (`server/routes/assets.ts:92–94,141–145`; `server/routes/feeds.ts:11–14`; `server/feeds.ts:329–335`; `server/routes/coast-pages.ts:12–16`; `server/coast-data.ts:311–317`; `server/routes/advisor.ts:145–163`; HTTP model: RFC 9110 §§9.3.3,15.1 and RFC 9111 §§3,4.2.2). |

## R4. Ranked gaps

1. **Withdrawal is not replacement.** Content names avoid confusing versions but do not recall an old public URL with a year of freshness. Offline public copies are another path without a matching HTTP deadline. No withdrawal, purge or rights decision is made here (`server/feeds.ts:166–170,346–348`; `scripts/client-build.mjs:32–39`; `dist/sw.js:144–171,239–255,378–407`).
2. **Degraded replay outlasts the normal feed TTL.** A healthy miss consults the release, but an eligible cost-ceiling replay does not. The risk is up to seven days from save, not seven days of browser caching. Seafloor's live receipt is the useful negative control (`server/cost-ceiling.ts:38,111–145,169–218,234–251`; `server/feeds.ts:319–345`).
3. **Normal same-URL feed verification can see the previous release just after a change.** The gap is up to one normal edge TTL, not hours by itself: generation and ETag describe what answered, not freshness against the release pointer (`server/feeds.ts:207–240,312–322`; `tests/test_feeds_cache_first.mjs:94–137`).
4. **Missing headers are mostly narrow exceptions; static platform defaults are not proven here.** Bare missing responses can hide a newly valid URL for an implementation-dependent time. This is not an account/health JSON policy gap (`server/routes/feeds.ts:11–14`; `server/routes/assets.ts:92–114`; `server/routes/account.ts:13–43`; `server/http.ts:7`).

**One optional follow-up, no header change (estimate: 60–90 minutes):** extend only `tests/test_feeds_cache_first.mjs` with a synthetic warm-then-withdraw case. Existing cases check warm replacement and cold absence separately (lines 106–137); the composition should show the original body/generation while warm, then confirm that the first request at expiry reads the new release and returns 404 `no-store` without filling the cache. This catches a regression that replays the held file after ordinary expiry or negatively caches the withdrawn result. Offline: `node --test tests/test_feeds_cache_first.mjs` with local locked dependencies. This would document current behavior, not decide how long a withdrawal ought to take.
