These are source-level estimates, not Cloudflare quota accounting or latency measurements. Zero if the relevant gate is off unless noted; unlisted I/O is none on that path. Work dispatched to Actions, queue consumers, and Meta's later media downloads do not count against this invocation (`server/index.ts:26–67`; `server/watchdog.ts:104–109`; `server/advisor/social/publish.ts:173–178`).

The queue producer does **not** assess trips, fetch their regional inputs, or send Web Push here. The separate `queue` event performs checks, retries exceptions with a delay, and logs/acks dead letters (`server/index.ts:46–67`; `server/trip-queue.ts:89–125`). The scheduled handler binds the raw `FEEDS` bucket; it never enters HTTP cost-ceiling middleware, so it does not charge or consult the app's daily `cost-ceiling:r2-reads:<UTC day>` counter or use the last-known copies from that middleware. ## R2. Overruns, limits and alerts

- **No tick-wide deadline or lock in the handler.** It does not compare against the next quarter-hour, cancel tasks, serialize invocations, or resume from a saved step number. At a later tick it starts again with current time/state; the code has no overlap veto (overlap is possible if the platform starts a new tick before the previous one ends). Specific claims and leases are not a global lock. The trip owner scan has page sizes but no whole-loop cap; Advisor steps/slots await in order, and publish polls are per container, not a time budget for the whole branch (`server/index.ts:26–43`; `server/trip-queue.ts:41–54,70–83`; `server/advisor/cron.ts:128–150,223–253`; `server/advisor/social/publish.ts:69–82,124–131,159–170,210–232,498–508`).
- **If a limit presents as an ordinary failed I/O:** the catches above still apply, but later tasks may also need the exhausted service/quota. In particular, a failed slot lookup or claim goes straight to `advisor_cron_failed` and skips every later Advisor slot, not the already-started general branches. A thrown slot body normally releases its claim for a later eligible tick; if release fails the old claim can still suppress retry. A missed weekday/time window is not backfilled the following day. If a **hard runtime limit terminates the invocation**, unfinished work and not-yet-started Advisor steps/slots do not finish, and there is no guarantee of cleanup or the final analytics point. Completed writes/sends are not rolled back by this handler. For example, termination after the trip claim but before all batches send can leave the same publication marked unchanged on the next tick; the analogous slot claim can suppress retry that day. A held row can be left `sending`. These are source-derived interruption cases, not observed production incidents (`server/index.ts:30–43`; `server/trip-queue.ts:70–83`; `server/advisor/cron.ts:128–150,244–253`; `server/advisor/consumer.ts:1000–1021`). The checked-in Worker config does not set invocation CPU/subrequest limits (`git show 9e078e2bd4c2db659e0f6e175c33cd6b0fd18553:wrangler.jsonc`); effective account limits, scheduling guarantees and runtime outcome labels are platform settings, not verified offline. Platform reference: [Cloudflare Workers limits](https://developers.cloudflare.com/workers/platform/limits/).
- **What makes the invocation fail:** caught watchdog/trip throw (logged `Cron watchdog failed` / `Cron trip checks failed`), retention `failed`, trip `enqueue-failed`, or Advisor `error`. The handler attempts analytics first, then throws `cron run failed`; swallowing the `waitUntil` copy does not swallow the returned rejection. Missing bindings, ordinary skips, Advisor `partial`, stale feed without token, and a **non-204 dispatch response** (`dispatch-failed-<status>` in `Live feed watchdog`) do not alone fail the tick. Unknown run counts or network errors thrown by GitHub discovery/dispatch do fail it and no discovery guess is used. Trip logs `trip_check_schedule` except `no-queue`; releasing the trip marker on error is best effort and does not recall batches already sent (`server/index.ts:29–43`; `server/watchdog.ts:129–157`; `server/trip-queue.ts:75–83`; `server/advisor/cron.ts:215–253`).
- **Where to look:** Workers Logs console/outcome (`wrangler.jsonc:50–54`; deploy invocation-log switch at `scripts/wrangler_config.mjs:14,165`), optional analytics (`docs/cloudflare.md:138–153`) and the cron-failure alert described in `docs/cloudflare.md:164–166` (non-`ok` scheduled outcome at least once in an hour, where supported; not evidence of a configured recipient). Feed degradation/no token logs warnings, raw fallback failure has no separate log, and there is no final application log specific to a platform hard kill. Independent feed-freshness workflow/issue is a feed alarm, not proof the Worker tick finished (`server/watchdog.ts:112–121,138–156`; `docs/operations/runbooks/feed-stale.md:10–11`; `docs/production-operations.md:38–42`). Trip consumer/DLQ logs belong to other invocations (`server/trip-queue.ts:106–124`; `docs/operations/runbooks/trip-checks.md:12–21`).
