# Coherent R2 feed publication

Conditions, data and forecasts preserve their public `/feeds/<branch>/<path>` URLs and exact committed bytes. The R2 publisher stores unique bytes at `<prefix>/.r2-objects/<sha256>`, a canonical file-to-hash map at `<prefix>/.r2-releases/<generation>.json`, and one mutable `<prefix>/.r2-current.json` pointer. The generation is SHA-256 of the complete snapshot bytes. These reserved internal keys cannot be fetched through the public feed route.

The publisher verifies each new or reused object's actual byte hash and the snapshot bytes by read-back before committing the pointer. The pointer uses `If-Match` against the initially observed ETag, or `If-None-Match: *` on first publication. [Cloudflare documents both conditional PutObject operations](https://developers.cloudflare.com/r2/api/s3/api/). A conflicting upload fails without changing the winner's complete release. A lost final acknowledgment may mean the complete new release committed; read the current pointer/run evidence before retrying. Publishing the same snapshot verifies its object bytes without changing the pointer. Hash metadata and length alone cannot prove a prior upload was verified; even no-op retries read and hash stored bytes. This increases publication read traffic and protects against same-length corruption left by a failed attempt. Freshness still requires the existing public-feed verification and age checks; compare-and-swap does not prove an older source is newer.

## Compatible rollout

Deploy the reviewed Worker reader and publisher source together through normal main CI/deployment. Before first snapshot publication, readers use the existing R2 keys and GitHub fallback. New publishers never modify those legacy keys, so a publisher running before the new Worker deployment leaves the older Worker serving its complete prior copy. The new Worker starts using the snapshot when the next ordinary authorized live/daily publication commits its pointer. No bucket rebinding, credential, lifecycle or source-branch change is required. Old jobs still uploading legacy keys cannot change committed snapshots.

The request-scoped forecast reader pins the release for the entire forecast query, including all models and points. Unrelated feed HTTP requests can legitimately observe different complete releases; this is not a multi-prefix distributed transaction. Responses include `X-Feed-Generation`; immutable physical cache keys prevent one release's tile cache from being used with another release's manifest. Once a snapshot is active, missing referenced bytes, corrupt pointers/maps, or paths removed from its file map never fall back to mutable legacy/GitHub bytes. Missing paths return404, missing referenced objects503. The schema and provenance of feed documents do not change. Tile/seafloor publication retains its existing live rights/expiry/hash gate and separate publisher.

## Failure and rollback

An object-upload, read-back, snapshot-upload or conditional-pointer failure leaves the last committed coherent snapshot available. Partial uncommitted objects are unreferenced. Do not repair failure by overwriting immutable objects or deleting the current pointer. Investigate inconsistent existing objects without exposing private data. The normal publishing job fails and retains its attempt evidence.

A data rollback republishes the exact reviewed prior branch snapshot through the same publisher. Its unchanged objects are reused, the snapshot is verified, and the pointer commits conditionally. In-flight readers pinned to the outgoing release still complete because their bytes remain. Preserve source commits, prior release records and all objects. A Worker rollback to code predating this protocol serves frozen legacy keys and can be stale: verify public freshness and arrange the reviewed reader/publisher rollback together. Never equate a successful Worker smoke test with a feed-data rollback.

## Retention and verification

This source migration does not delete any existing stable key, immutable object or snapshot, and does not change R2 lifecycle rules. Objects removed from the current branch become unavailable at ordinary URLs while their bytes remain preserved for pinned readers and reviewed rollback. Existing legacy history/archive age rules do not match the internal object keys. Retained unique bytes will increase storage as feeds change; track bucket usage before approving a separate reachability-aware garbage collector. Do not apply an age-only lifecycle rule to immutable objects: unchanged bytes can remain current indefinitely. This preserves data and avoids introducing destructive cleanup in the repair.

Verification must record the actual deployed Worker SHA, ordinary publication source and completion, the public route's generation/source plus expected `run_id`/publication clocks, and any failure. The source tests cover upload-phase failure, corrupted read-back, concurrent winner/loser, lost acknowledgment, rollback and readers held across promotion/removal. Safe release verification uses existing jobs and public feeds; do not create a competing schedule or acquire provider data just to exercise this protocol.
