## What changed (READ)

- `web/map/aerial.ts`: where the page passes `sharp` (the map stage does), a new Aerial draw first asks each 512 px tile at `size=256,256` (same template, host, format, dates and paint; its own `:preview` source). Morro Bay's opening four tiles: 280 KB instead of 1.14 MB (all four are PNG because each holds open water). When `sharp` turns true the full source is added above the preview, and the preview is removed at the next map `idle` (`skippercast-aerial-sharp` mark). Never blank. The png32 fallback keeps its one retry, at the stage it failed in; a base that failed for good asks for nothing more. Without `sharp` the base behaves exactly as before.
- `createSharpStart` (aerial.ts), wired in `web/app/MapStage.tsx`: `sharp` turns true once the Chart has first settled and the seafloor's first view has landed (`seafloorState` leaves `checking`), or 10 s after that settle. Latched. While the preview is still drawn (`aerialSoft`), the Chart host stays `aria-busy` after its first idle, so "not busy" still means the final first-view imagery (review round 1; the `skippercast-chart-idle` mark is unchanged).
- `web/map/seafloor.ts`: at most 2 tile ranges in flight; the latest view's and the view centre's ranges first. Tiles are still read back in `tilesForBounds` order, so the drawn features and every publication, expiry, rights and hold check are unchanged. Adds the `skippercast-seafloor-drawn` mark.

## The seafloor half of the proposal (MEASURED + READ)

The proposal asked for "a coarser seafloor level first". The published archive cannot give that: it is built with `precise=True` (no simplification at any zoom), so its lower zooms are not lighter (z11 2.11 MB, z12 2.16 MB, z10 1.94 MB in 4 tiles of up to 941 KB; `pmtiles_sizes.mjs` on the live archive). The 609 KB tile (12/672/1618) lies inside the phone's open band, so drawing only the visible band would not drop it either. A lighter first level needs a re-published, generalised archive (PERF-BASELINE-1 P13), which is outside this change.

The z12 seafloor cannot be complete by 12 s on this profile in any request order (MEASURED, `sfbound.py` on the same receipts): its first range is asked at 7.11 s cold (median; after the publication, screened-reach and header checks, behind SCB-12's start gate), and its ranges total 1,220,799 bytes, which is 5.96 s of the 204,800 B/s link with nothing else on it. The earliest possible completion is therefore 13.07 s cold (13.02–13.18) even if every other request waited; 8.07 s warm. Reaching 12 s would need fewer seafloor bytes (a generalised archive) or an earlier start (moving SCB-12's gate), both outside these files.

What this change does instead is order the seafloor's ranges so they stop crowding out the map's own base tiles: on main the cold first idle waited for the basemap tiles queued behind ten seafloor ranges.

## Trade-offs (MEASURED)

- The opening view's aerial is softer from about 11.6 s until about 25.8 s cold; on main it was sharp when the map first finished, at about 19 s. The full image waits for the seafloor's first view on purpose (the seafloor candidates are the Boat view's content; the aerial is context). Starting it at the first settle instead would bring the sharp image earlier and the seafloor later.
- Warm: chart idle +0.25 s (still under 3.5 s) and seafloor +1.1 s, because two ranges at a time use the link less fully when nothing else competes.
- `skippercast-aerial-sharp` fires at the first idle after the 19 s flyover, so it reads about 30.7 s cold; the opening view's full tiles were in at about 25.8 s.

## Method and limits (READ)

SCB-12's harness, unchanged: built Vite assets served by a local Brotli HTTP/1.1 server, every public data request a live GET to skippercast.com, real USGS imagery; CDP CPU 4x, 150 ms latency, 204,800 B/s down, 96,000 B/s up, 390x844 DPR 3, touch; fresh browser context per cold run, warm tab 3 s later in the same context; flyover left on; first-run card set as SCB-02/SCB-12. One region (Morro Bay), software WebGL, shared host (1-minute load 5–15), HTTP/1.1 locally where production is HTTP/2, live upstream answers that change. Not a real phone.
